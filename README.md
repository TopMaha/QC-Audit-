## วงจรการทำงาน — 5 ขั้นตอน

ทุกใบแจ้งมีแถบขั้นตอนบนสุดของหน้า บอกว่างานอยู่ขั้นไหน รอใคร และแต่ละขั้นเกิดเมื่อไร
แต่ละขั้นมีปุ่มให้กดปุ่มเดียว ผู้ใช้จึงไม่ต้องเดาว่าต้องทำอะไรต่อ

```
 ① QC พบปัญหา ──► ② VSM รับทราบ ──► ③ กำลังแก้ไข ──► ④ แก้ไขเสร็จแล้ว ──► ⑤ QC ตรวจรับ
   [รอ VSM รับทราบ]   กดปุ่ม "รับทราบ"    กดปุ่ม "เริ่มแก้ไข"   ส่งรูปหลังแก้ + คำอธิบาย   [ปิดงานแล้ว]
         │                                        ▲                     │
   เด้งหาหัวหน้าสาย                                 └──── QC ตีกลับ ◄──────┤ (ต้องบอกเหตุผล
                                                     เด้งกลับหาสาย          │  เด้งหา QC ผู้เปิดใบ)
```

- **ปิดงานบังคับแค่สองอย่าง** — รูปหลังแก้ไขอย่างน้อย 1 รูป + คำอธิบายการแก้ไข
  (ช่องสาเหตุถูกเอาออกจากหน้าจอแล้ว ข้อมูลเก่าที่เคยกรอกสาเหตุยังแสดงครบ)
- "รับทราบ" กับ "กำลังแก้ไข" ใช้สถานะ `in_progress` เดียวกันในฐานข้อมูล แยกด้วยคอลัมน์
  `started_at` เพราะการเพิ่มค่าใน CHECK ของ SQLite ต้องสร้างตาราง `qc_issues` ใหม่ทั้งตาราง
  ซึ่งเสี่ยงกับตารางลูกที่ผูก CASCADE ไว้ (ดู `stageOf()` ใน `src/lib/calc.ts`)
- ทุกครั้งที่แก้ไขถูกเก็บแยกเป็นประวัติ ไม่ได้ทับของเดิม จึงย้อนดูได้ว่าถูกตีกลับกี่รอบและเพราะอะไร

### หัวหน้าสาย VSM และการแจ้งเตือนแบบเด้ง

ผู้ดูแลระบบกำหนดหัวหน้าของแต่ละสายได้ที่ **ตั้งค่า › หัวหน้าสาย** (สายละหลายคนได้)
หัวหน้าสายเป็นคนแผนกไหนก็ได้ และได้สิทธิ์รับทราบ/แก้ไขใบของสายนั้นทันที
คนที่ยังเข้าระบบไม่ได้จะถูกเปิดสิทธิ์ให้อัตโนมัติ ส่วน VSM ของสายที่เข้าระบบได้ก็ได้รับแจ้งเหมือนเดิม

งานเด้งสองทาง
- **ในแอป** — กล่องเด้งกลางจอพร้อมรูป เลขที่ใบ และหมายเลขเครื่อง ทันทีที่มีงานเข้า
  (แอปถามเซิร์ฟเวอร์ทุกนาทีว่ามีอะไรใหม่ อ่านแถวเดียว แล้วค่อยดึงข้อมูลชุดใหญ่เมื่อมีจริง)
- **บนมือถือแม้ปิดแอป** (Web Push) — กด "เปิดการแจ้งเตือน" ในหน้างานของฉันครั้งเดียว
  Android ใช้ได้ทันที · iPhone ต้อง "เพิ่มลงหน้าจอโฮม" แล้วเปิดจากไอคอนก่อน (iOS 16.4+)
  ออกจากระบบแล้วเครื่องนั้นเลิกรับงานของคนเดิมเอง

### ส่งออก Excel

ปุ่ม **ส่งออก Excel** อยู่ที่แดชบอร์ด (ช่วงสัปดาห์/เดือนที่เลือก) และหน้ารายงาน
ได้ไฟล์ `.xlsx` ที่มี
- **สรุปภาพรวม** — ตัวเลขหลัก · ตารางราย VSM แยกตาม 5 ขั้นตอน · กราฟ · ประเภทข้อบกพร่องและเครื่องจักรที่พบบ่อย
- **VSM1–VSM4** — ทุกใบของสาย: ปัญหา · เครื่องจักร · ลำดับการดำเนินการพร้อมเวลา · การแก้ไข · รูป **BEFORE / AFTER** ในเซลล์
- **ข้อมูลทั้งหมด** — ตารางแบนสำหรับกรองหรือทำ Pivot ต่อ

ไฟล์สร้างในเบราว์เซอร์ (ExcelJS โหลดเฉพาะตอนกดส่งออก) รูปถูกย่อก่อนใส่ ไฟล์จึงไม่บวม

### สิ่งที่ถูกบันทึกไว้ในแต่ละรอบ

นอกจากผลตรวจ ระบบเก็บ **บริบทการผลิต** ไปกับทั้งรอบตรวจและใบแจ้ง — กะ (A/B/C) ·
เครื่องจักร · รุ่นสินค้า · ผู้ปฏิบัติงาน ทุกช่องไม่บังคับกรอก แต่ถ้ากรอกจะเทียบได้ว่า
กะไหนหรือเครื่องไหนพบของเสียมากกว่ากัน ซึ่งดูจากจำนวนใบแจ้งอย่างเดียวไม่มีทางรู้

- **กะเติมให้อัตโนมัติจากเวลาที่บันทึก** (A 08:00–15:59 · B 16:00–23:59 · C 00:00–07:59)
  แก้เองได้เสมอ สำหรับรอบที่คร่อมเวลาเปลี่ยนกะหรือบันทึกย้อนหลัง
- **เก็บซ้ำทั้งสองตารางโดยตั้งใจ** เพราะใบแจ้งนอกรอบไม่มีรอบตรวจให้สืบทอดค่า
  และรอบที่ผ่าน (ไม่มีใบแจ้ง) ก็ต้องรู้บริบทเช่นกัน
- ใบแจ้งที่เปิดจากรอบตรวจ **สืบทอดบริบทจากรอบเสมอ** ทั้งฝั่งหน้าจอและฝั่ง Worker
  จึงไม่มีทางเกิดใบที่บอกว่าเกิดคนละกะกับรอบตรวจที่มันสังกัด

**บันทึกเสียง** — QC กดอัดเสียงบรรยายข้อบกพร่องแนบไปกับใบแจ้งได้ (สูงสุด 2 นาที)
หน้าไลน์คนใส่ถุงมือและถือของอยู่อีกข้าง พูดใส่จึงเร็วกว่าพิมพ์และได้รายละเอียดมากกว่า
ไฟล์เสียงใช้เส้นทางเดียวกับรูปทุกขั้น (เก็บในเครื่องก่อน แล้วซิงก์ขึ้น R2 เอง)

> เสียงเป็นของแถม ไม่ใช่ของบังคับ — ไมโครโฟนใช้ไม่ได้หรือเซิร์ฟเวอร์ไม่รับ
> ก็ยังบันทึกใบแจ้งได้ตามปกติ ตัวซิงก์จะส่งใบขึ้นไปโดยไม่มีเสียงแทนที่จะทิ้งทั้งใบ

**ร่างอัตโนมัติ** — สิ่งที่กรอกค้างไว้ในหน้าบันทึกผลตรวจถูกเก็บลงเครื่องเป็นระยะ
มีสายเข้า สลับแอป หรือเบราว์เซอร์คืนหน่วยความจำแล้วกลับมา จะได้ของเดิมคืนทั้งหมด
รวมถึงรูปที่ถ่ายไว้แล้ว พร้อมแถบบอกว่ากู้คืนมาและปุ่ม "เริ่มใหม่" ถ้าไม่ต้องการ
(ร่างแยกตามคนและตามโหมด · ถูกลบทิ้งทันทีที่บันทึกสำเร็จ · ไม่ซิงก์ขึ้นเซิร์ฟเวอร์
และไม่นับในรายงานใด ๆ)

### กติกาที่ระบบบังคับ

| กติกา | เหตุผล |
|---|---|
| ใบแจ้งต้องมีรูปหลักฐานอย่างน้อย 1 รูป | ไม่มีรูปแล้ว VSM ต้องเดินมาถามว่าอยู่ตรงไหน |
| ใบแจ้งต้องมีหมายเลขเครื่องจักร (ไม่เกี่ยวกับเครื่องใส่ `-`) | VSM ต้องรู้ว่าเดินไปแก้ที่เครื่องไหน |
| งานแก้ไขต้องมีรูปยืนยันอย่างน้อย 1 รูป | QC ตรวจรับจากรูป ไม่ใช่จากคำบอกเล่า |
| การตีกลับต้องระบุเหตุผล | ไม่งั้น VSM ต้องเดา แล้ววนถูกตีกลับซ้ำ |
| รับทราบ/เริ่มแก้/ส่งงานแก้ไข ได้เฉพาะ VSM ของสายนั้นและหัวหน้าสายที่กำหนดไว้ | กันสายหนึ่งปิดงานแทนอีกสาย |
| กำหนดหัวหน้าสายได้เฉพาะผู้ดูแลระบบ | คนที่ได้งานเด้งไปหาต้องถูกเลือกโดยคนที่รับผิดชอบระบบ |
| ตรวจรับได้เฉพาะ QC | คนแก้กับคนตรวจต้องไม่ใช่คนเดียวกัน |
| ใบที่ปิดหรือยกเลิกแล้วเปลี่ยนสถานะไม่ได้ | เป็นหลักฐานแล้ว |
| จำนวนที่บกพร่องต้องไม่เกินจำนวนที่ตรวจ | ไม่งั้น % ของเสียเกิน 100 |
| เลือกประเภทข้อบกพร่องได้สูงสุด 3 | บังคับให้ระบุสาเหตุหลักจริง ๆ |

กติกาทุกข้อถูกตรวจสองชั้น — ที่หน้าจอเพื่อบอกผู้ใช้ทันที และที่ Worker อีกครั้ง
เพราะโทเคนของแอปเป็นโทเคนร่วม ใครที่เปิดหน้าเว็บได้ก็ยิง API ตรงได้

## การเข้าสู่ระบบ — รหัสพนักงานอย่างเดียว

- กรอกรหัสพนักงานแล้วกดเข้า **ไม่มี PIN** — เข้าได้เมื่อรหัสมีในทะเบียน บัญชียังใช้งานอยู่ และเปิดสิทธิ์เข้าแอปแล้ว
- ผู้ดูแลระบบ (`/admin`) ใช้รหัสพนักงานที่อยู่ในทะเบียนผู้ดูแลระบบ
- เข้าได้แล้วเซิร์ฟเวอร์ออก **โทเคนเซสชัน** ให้ ทุกคำขอต้องแนบโทเคนนี้ (header `X-Session`)
  เซิร์ฟเวอร์รู้ว่าใครทำอะไรจากโทเคนเท่านั้น ถอนสิทธิ์/ปิดบัญชีแล้วมีผลในคำขอถัดไปทันที
- ทะเบียนพนักงานและรายชื่อผู้ดูแลระบบ **ไม่อยู่ในไฟล์เว็บแล้ว** — ดึงจากเซิร์ฟเวอร์หลังเข้าสู่ระบบเท่านั้น
  (`src/lib/roster.ts` ใช้เฉพาะโหมดในเครื่อง และถูกตัดออกจาก build ของจริงทั้งไฟล์ — ดู `boot()` ใน `src/main.tsx`)

## บทบาทผู้ใช้

| บทบาท | เห็นอะไร | ทำอะไรได้ |
|---|---|---|
| **QC** (แผนก Quality Control) | ทุกใบแจ้ง | บันทึกผลตรวจ · เปิดใบแจ้ง · ตรวจรับ/ตีกลับ · แก้ใบที่ตัวเองเปิด |
| **VSM** (สาย VSM1–VSM4) | ใบแจ้งของสายตัวเอง | รับทราบ · เริ่มแก้ไข · ส่งรูปหลังแก้ + คำอธิบาย |
| **หัวหน้าสาย** (กำหนดใน ตั้งค่า › หัวหน้าสาย) | ใบแจ้งของสายที่ดูแล | เหมือน VSM ของสายนั้น + ได้รับงานเด้ง — แผนกใดก็ได้ |
| **ผู้ติดตามผล** | ทุกใบแจ้ง (อ่านอย่างเดียว) | — |
| **ผู้ดูแลระบบ** (เข้าที่ `/admin`) | ทั้งหมด | บันทึกผลตรวจ · เปิดใบแจ้ง · จัดการทะเบียน · ตั้งค่า · ส่งออกรายงาน · ดูบันทึกระบบ |

บทบาทตั้งต้นมาจากแผนกในทะเบียน PSIF แล้วผู้ดูแลระบบแก้รายคนได้จากหน้าตั้งค่า

> **หมายเหตุเรื่องสิทธิ์ผู้ดูแลระบบ**
> คนที่อยู่ในทะเบียนผู้ดูแลระบบ **บันทึกผลตรวจและเปิดใบแจ้งได้เสมอ** แม้แผนกจะไม่ใช่
> Quality Control (ผู้ดูแลระบบส่วนใหญ่สังกัดสาย VSM) และแก้ใบที่ตัวเองเปิดไว้ได้ด้วย
>
> ส่วนสิทธิ์ที่เหลือยังยึดบทบาทของพนักงานคนนั้นเป็นหลัก เพราะทุกคำขอแนบรหัสพนักงานไปเสมอ
> โดยเฉพาะ **การตรวจรับงานแก้ไขยังเป็นของ QC เท่านั้น** ตามกติกาคนแก้กับคนตรวจต้องไม่ใช่คนเดียวกัน
> ถ้าต้องทำแทนผู้ใช้ทุกอย่าง ต้องออกจากระบบก่อนแล้วเข้าที่ `/admin`

## เริ่มพัฒนา

```bash
npm install
npm run dev          # http://localhost:8081
```

ไม่ต้องตั้งค่าอะไรเพิ่ม — ถ้าไม่มี `.env.local` แอปจะทำงานใน **โหมดในเครื่อง**
คือเก็บข้อมูลไว้ใน localStorage ของเบราว์เซอร์อย่างเดียว เปิดดูและทดลองใช้ได้ครบทุกหน้า

รหัสสำหรับทดลองในโหมดในเครื่อง (ข้อมูลสมมติจาก `src/lib/roster.data.example.ts` — ไม่มี PIN):

| รหัส | บทบาท |
|---|---|
| `Q-001` | QC ผู้ตรวจ |
| `V-201` | VSM ผู้แก้ไข (สาย VSM2) |
| `A-001` | ผู้ดูแลระบบ (เข้าที่ `/admin`) |

พิมพ์ตัวเล็กหรือไม่ใส่ขีดกลางก็ได้ — ระบบตัดขีดกลางและตัวพิมพ์ออกก่อนเทียบ

> **ทะเบียนพนักงานจริงไม่อยู่ใน git** — อยู่ใน `src/lib/roster.data.ts` และ `worker/seed.sql`
> ซึ่งอยู่ใน `.gitignore` (มีชื่อ-รหัสทั้งโรงงานและรายชื่อผู้ดูแลระบบ) เครื่องที่ clone ไปใหม่
> จะใช้ข้อมูลตัวอย่างอัตโนมัติ ถ้าต้องการทะเบียนจริงให้ขอไฟล์ `roster.data.ts` จากผู้ดูแลระบบ

## ต่อระบบหลังบ้าน (Cloudflare Worker + D1 + R2)

### 1. สร้างทรัพยากรบน Cloudflare

```bash
cd worker
npx wrangler d1 create qc-audit-line
npx wrangler r2 bucket create qc-audit-photos
```

นำ `database_id` ที่ได้ไปใส่ใน `worker/wrangler.toml`

### 2. สร้างตารางและใส่ข้อมูลตั้งต้น

```bash
cd worker
npm install
npm run db:schema    # สร้างตาราง
npm run db:seed      # ทะเบียนพนักงาน 393 คน · จุดตรวจ 31 จุด · ประเภทข้อบกพร่อง 10 รายการ
```

> **ฐานข้อมูลที่ขึ้นระบบไปแล้วต้องรันคำสั่งปรับโครงเพิ่มหนึ่งครั้ง**
>
> ```bash
> cd worker
> npm run db:migrate       # 001 เพิ่มคอลัมน์บริบทการผลิต + บันทึกเสียง
> npm run db:migrate:002   # 002 ขั้นตอน 5 ขั้น (started_at) + หัวหน้าสาย + การแจ้งเตือนแบบเด้ง
> npm run db:migrate:003   # 003 เซสชัน (ตาราง employee_pins ในไฟล์นี้ไม่ได้ใช้แล้ว)
> ```
>
> รันตามลำดับ 001 แล้ว 002 เสมอ
> `db:schema` ใช้ `CREATE TABLE IF NOT EXISTS` จึงไม่เพิ่มคอลัมน์ให้ตารางที่มีอยู่แล้ว
> ฐานที่สร้างใหม่ตั้งแต่ต้นไม่ต้องรัน (schema.sql มีคอลัมน์ชุดนี้อยู่แล้ว)
> รันซ้ำจะได้ error `duplicate column name` ซึ่งแปลว่าปรับไปแล้ว ไม่ใช่ความเสียหาย
>
> **ต้องรันก่อน deploy Worker ตัวใหม่** ไม่งั้น Worker จะเขียนลงคอลัมน์ที่ยังไม่มี

### 3. ตั้งโทเคนแล้ว deploy

```bash
npx wrangler secret put AUTH_TOKEN          # ตั้งค่าลับ ห้ามใส่ใน wrangler.toml
npx wrangler secret put VAPID_PRIVATE_JWK   # กุญแจลับของการแจ้งเตือนแบบเด้ง (JWK ของ P-256)
npx wrangler deploy
```

กุญแจสาธารณะคู่กัน (`VAPID_PUBLIC_KEY`) อยู่ใน `[vars]` ของ `worker/wrangler.toml`
ไม่ได้ตั้ง `VAPID_PRIVATE_JWK` = ระบบทำงานปกติ แค่ไม่มีการแจ้งเตือนตอนปิดแอป
ถ้าต้องสร้างคู่กุญแจใหม่ ทุกเครื่องต้องกดเปิดการแจ้งเตือนใหม่อีกครั้ง

```bash
node -e "const{generateKeyPairSync:g}=require('crypto');const{privateKey:k,publicKey:p}=g('ec',{namedCurve:'prime256v1'});const j=k.export({format:'jwk'}),q=p.export({format:'jwk'});console.log('PRIVATE',JSON.stringify(j));console.log('PUBLIC',Buffer.concat([Buffer.from([4]),Buffer.from(q.x,'base64url'),Buffer.from(q.y,'base64url')]).toString('base64url'))"
```

### 4. หน้าเว็บ — GitHub Pages

push เข้า `main` แล้ว `.github/workflows/deploy.yml` build และขึ้น https://topmaha.github.io/QC-Audit- ให้เอง
(ใช้เวลาราว 1–2 นาที ดูผลได้ที่แท็บ Actions)

> https://qc-audit-line.pages.dev (Cloudflare Pages) **เลิกใช้แล้ว** — `npm run deploy` คือสคริปต์ขึ้นที่นั่น ไม่ต้องรัน
> `.env.local` (`VITE_API_URL` + `VITE_AUTH_TOKEN`) ยังใช้กับ `npm run dev` ในเครื่อง

ตั้งใน repo ก่อนครั้งเดียว:

1. **Settings → Pages → Build and deployment → Source** = `GitHub Actions`
2. **Settings → Secrets and variables → Actions → New repository secret**
   ชื่อ `VITE_AUTH_TOKEN` ค่า = เฉพาะตัวโทเคนที่อยู่หลัง `VITE_AUTH_TOKEN=` ใน `.env.local`
   (ไม่ใส่ชื่อตัวแปร เครื่องหมาย `=` หรือเครื่องหมายคำพูด — ถ้าผิดรูป workflow จะล้มพร้อมบอกสาเหตุ)
3. แท็บ **Actions → Deploy to GitHub Pages → Run workflow** (หรือ push อะไรก็ได้เข้า `main`)

> แอปเสิร์ฟใต้ `/QC-Audit-/` ไม่ใช่ root — build ด้วย `npm run build:ghpages`
> path ใน `public/` (manifest · service worker) จึงเขียนแบบอิงตำแหน่งไฟล์ ห้ามขึ้นต้นด้วย `/`
> `https://topmaha.github.io` อยู่ใน `ALLOWED_ORIGIN` ของ Worker แล้ว

## การซิงก์และการใช้งานออฟไลน์

หน้าจอทุกหน้าอ่าน–เขียนกับสำเนาในเครื่องเท่านั้น การส่งขึ้นเซิร์ฟเวอร์เป็นงานเบื้องหลัง

- บันทึกงานได้ทันทีแม้ไม่มีสัญญาณ — งานเข้าคิวใน IndexedDB
- กลับมาออนไลน์แล้วส่งเองอัตโนมัติ (และทุก 60 วินาที เผื่อเบราว์เซอร์ไม่แจ้ง event)
- ป้ายสถานะการซิงก์อยู่บนแถบหัวเรื่องตลอดเวลา แตะเพื่อลองส่งใหม่ได้
- `id` ถูกสร้างจากเครื่องผู้ใช้ การส่งซ้ำจากคิวจึงไม่ทำให้เกิดข้อมูลซ้ำ
- **เลขที่เอกสาร** ที่ออกจากเครื่องเป็นเลขชั่วคราว เมื่อซิงก์แล้วเซิร์ฟเวอร์จะออกเลข
  ทางการทับให้ (เครื่องแต่ละเครื่องนับของตัวเองจึงชนกันได้)
- **ประวัติการแก้ไข** ถูกดึงจากเซิร์ฟเวอร์มาทับทุกรอบซิงก์ (ส่งคิวขึ้นให้หมดก่อนเสมอ
  แล้วค่อยดึงลง) ผู้ดูแลจึงเห็นการแก้ไขของทุกคน ไม่ใช่แค่ของเครื่องตัวเอง —
  ดูได้ที่ **ตั้งค่า › บันทึกระบบ** พร้อมตัวกรองตามตารางและช่องค้นหา

## ตัวเลขบนแดชบอร์ด

| ตัวเลข | สูตร |
|---|---|
| ปิดตรงกำหนด % | ใบที่ปิดภายในกำหนด ÷ ใบที่ปิดแล้วทั้งหมด × 100 |
| อัตราพบข้อบกพร่อง % | รอบตรวจที่พบข้อบกพร่อง ÷ รอบตรวจทั้งหมด × 100 |
| ถูกตีกลับ % | ใบที่ถูกตีกลับอย่างน้อยหนึ่งครั้ง ÷ ใบทั้งหมด × 100 |
| เวลาปิดเฉลี่ย | วันเฉลี่ยตั้งแต่วันที่พบจนถึงวันที่ QC ตรวจรับผ่าน |

ทุกเปอร์เซ็นต์ปัดลง · ใบที่ยกเลิกไม่ถูกนับในตัวหารของทุกสูตร

**อันดับของสาย VSM เรียงตามอัตราปิดตรงกำหนด ไม่ใช่จำนวนปัญหาที่พบ** — โดยตั้งใจ
เพราะสายที่ถูกตรวจถี่กว่าย่อมเจอมากกว่าโดยธรรมชาติ ถ้าเอาจำนวนมาจัดอันดับ
จะกลายเป็นการลงโทษสายที่ถูกตรวจบ่อย แล้วทุกคนจะเริ่มกดดันให้ QC ตรวจน้อยลง

## ข้อจำกัดที่ควรรู้

- **ไม่มี PIN** — ใครรู้รหัสพนักงานของคนที่เปิดสิทธิ์ไว้ก็เข้าระบบในนามคนนั้นได้ (รวมถึง `/admin`
  ถ้ารู้รหัสของผู้ดูแลระบบ) ประวัติการเข้าระบบยังถูกบันทึกทุกครั้งที่หน้าตั้งค่า
- **การเข้าสู่ระบบต้องใช้เน็ต** เพราะเซิร์ฟเวอร์เป็นคนออกโทเคนเซสชัน
  เข้าได้แล้วเซสชันอยู่ 60 วันและต่ออายุเองเมื่อใช้งาน ระหว่างนั้นใช้งานออฟไลน์ได้ตามปกติ
- **เปิดสิทธิ์ไว้แค่ 83 จาก 393 คน** (QC ทุกคน + ระดับหัวหน้าของสาย VSM + หัวหน้าสายที่กำหนด)
  ที่เหลือผู้ดูแลระบบเปิดเพิ่มรายคนได้
- โทเคนร่วม (`VITE_AUTH_TOKEN`) ยังอยู่ในไฟล์เว็บ แต่ตอนนี้เป็นแค่ชั้นแรก — ทุกคำขอต้องมีเซสชันรายคนด้วย
